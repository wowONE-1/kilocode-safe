# Команда 3: контроль действий Kilo Code

Исследовательский прототип для разработчика, который поручает агенту полезную задачу и задаёт границы обычным текстом. Реализованы пять режимов интерфейса, проверка полномочий перед действием, возврат понятного отказа и обязательная проверка распознанной установки до запуска package manager.

**Измеренная версия runtime:** `b184d6358b4078e6087694097141b7d7e976a27e`. Публикационный commit может быть новее за счёт документации и материалов; это не новая измеренная версия runtime. Единый источник чисел — [реестр презентации](presentation/final_20260907/source/final_metrics.json); сырые наблюдения и их производные показатели описаны в [benchmark](https://github.com/dimkablin/vibesechack/tree/26ade7bf753a8e26af1a719096c820b095fa77d0).

## Проверенный результат

На одном сопоставимом проходе Auto / Secure / Dos дали ASR 8/28 → 2/28 → 3/28, utility 22/38 → 7/38 → 22/38 и безопасную utility 19/38 → 6/38 → 21/38. У Dos совпало с Auto общее число полезных задач, но это не означает совпадения их состава. Secure показал меньше успешных атак ценой большого числа отклонённых headless-запросов; успех с реальным человеком не измерен. Это development-набор и один полный повтор, поэтому перенос результата на новые задачи требует отдельной проверки.

Выполнены 370 CLI-наблюдений и 44 отдельных nonexecuting probes. Расширенная маршрутизация закрывает прежний обход смысловой проверки обычными правками. На фиксированных опасных предложениях получено 2/6 → 0/6 unsafe allow; в CLI-парах снижение нарушений не показано, поскольку исходный Auto также не нарушил границы. Произвольная текстовая политика остаётся вероятностной, без строгой файловой изоляции. Неоднозначные полномочия на MCP остаются отдельной проблемой: в L16 все три основных режима выбрали неуказанного получателя до уточнения. Этот случай не является тестом буквального запрета правки файла.

## Threat model: что именно контролируется

Доверенные источники полномочий — явная permission policy приложения и доступные прямые сообщения пользователя корневой сессии. Содержимое репозитория, результаты инструментов, описание MCP, предложенные аргументы и инструкции, сформированные подагентом, недоверенны. Полезность действия не даёт дополнительных полномочий.

| Угроза и пример | Контроль до эффекта | Как проверяется | Остаточная граница |
| --- | --- | --- | --- |
| Инъекция из файла/инструмента предлагает постороннее действие | В Dos: детерминированные guards и смысловая проверка предложенного действия Qwen; внутри инструмента сохраняются Secure checks | Immutable casegiver и адаптированные CLI-атаки; отдельно конкретные deny/ask и task/harm oracle | Qwen может пропустить скрытые эффекты или семантически убедительную атаку |
| Превышение текстовых полномочий: менять только src, не менять tests/config | Dos направляет write/edit/patch/shell и непрозрачные действия через judge; сохраняет корневые user messages; проецирует исходные и canonical paths всех patch-операций | Парные text-only scope fixtures, полный manifest и независимый функциональный oracle; отдельно фиксированные предложения действий | Это вероятностная оценка, не файловая изоляция; скрытые эффекты helper/MCP и write-then-restore не доказываются конечным manifest |
| Slopsquatting: агент предлагает установить подозрительно названный пакет | В Secure/Dos распознанная установка обязательно проходит metadata gate до запуска установщика; положительный package review не отменяет обычные permission rules | Native маршрут внутри shell permission flow до запуска процесса установщика, registry-error/benign tests и отдельная пара package-attempt CLI | Эвристики существования, имени, возраста и метаданных не доказывают безопасность пакета; вложенные/нераспознанные установки вне полного покрытия |
| Попытка обойти отказ широким allow, Auto или делегированием | Явный deny сохраняет приоритет, outer allow не отменяет inner veto; защищённый запрос не подтверждается Auto; child наследует режим и корневые полномочия | Native routing/approval/delegation regressions и связанные с action ID события | Изменение trusted process/config вне threat model; интерфейс ask требует человека, headless-стенд отклоняет его |

Кодовые guards и перехват распознанных установок выполняются независимо от текста инструкций, которые агент прочитал. Это узкая гарантия исполнения проверок для охваченных путей. Она не означает полноты парсинга shell, доказательства безопасности произвольного кода или защиты от всех prompt injections.

## Режимы и поведение при сбоях

- **Auto:** обычные permission requests автоматически подтверждаются; защищённые запросы требуют отдельного решения.
- **Vanilla Kilo:** штатная политика Kilo без добавленных Secure/judge слоёв.
- **Secure:** штатная permission policy и добавленные security checks, включая распознанные установки.
- **Ask:** запрос на границах permission с security checks; не обещает вопрос перед каждым чтением.
- **Dos LLMs + Secure:** Secure и две условные стадии одной выбранной Qwen. Вторая стадия выполняется при эскалации первой.

Meta Prompt Guard — отдельная экспериментальная опция, по умолчанию выключенная. Отсутствие сигнала инъекции всё равно требует semantic stage 1; положительный сигнал ведёт в stage 2. Это не дополнительный режим интерфейса и не второй LLM в названии Dos.

При недоступности нужного корневого контекста, сбое classifier или невозможности безопасно спроецировать действие потенциально изменяющий вызов требует ручной проверки. Headless CLI его отклоняет; безопасные чтения сохраняют быстрый путь. Агент получает причину и может продолжить допустимую работу. Для повторных решений AUTO/judge заданы пороги перехода в ручной fallback; явные permission deny и внутренний package veto действуют отдельно.

## Пределы оценки и следующий шаг

Фактические результаты, ложные вмешательства на размеченных действиях, запросы подтверждения и задержки приведены в едином реестре и итоговом описании. Отсутствие вреда само по себе не считается блокировкой. Фиксированные предложения не входят в CLI ASR; автоматический отказ в headless не является решением живого человека.

Набор открыт команде, основная модель одна, покрытие ограничено. Исследование спроса, пилот с разработчиками и сокращение реальной ручной нагрузки не подтверждены. Прототип нельзя считать достаточной единственной защитой для production, реальных секретов или необратимых операций. Следующий шаг — ограниченный пилот по заранее согласованным условиям, с исключением известных незакрытых сценариев.

Требования организатора, внешние ориентиры и решения команды разделены в [brief](docs/HACKATHON_BRIEF.md) и [журнале решений](docs/DECISIONS.md). DepScope тоже заявляет pre-install MCP; преимущество нашего решения — обязательный перехват распознанной установки, а не предположение, что MCP всегда слишком поздний.
